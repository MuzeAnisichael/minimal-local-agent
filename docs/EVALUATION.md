# 评测

评测回答一个问题：在**同一个模型、同一份预算**下，换一种运行策略，任务成功率和成本会怎样变化。
运行时机制（续跑、对账、重试、重新规划、记忆）是否真的起作用，也靠这套评测做回归。

## 运行

```bash
mla eval --offline --out eval-report.json            # 脚本模型，结果确定，CI 每次都跑
mla eval --model deepseek --out deepseek.json        # 真实模型：固定 agent.toml 里的一个模型
mla eval --offline --only single_edit,multi_file     # 只跑部分任务族
mla eval --offline --strategies baseline,recovery    # 只比较部分策略
mla eval --offline --no-faults --repeat 3            # 不注入故障，每个用例跑 3 次
```

需要在仓库根目录运行（默认读取 `evals/families/`，可用 `--families` 指定其他目录）。

## 任务族

评测集在 `evals/families/`，每个 JSON 文件是一个任务族，共 6 个任务族、18 个用例，其中 9 个注入故障：

| 任务族 | 内容 | 注入的故障 |
| --- | --- | --- |
| `read_qa` 只读问答 | 读取工作区文件回答问题，不产生副作用 | 非法工具调用、读之前崩溃 |
| `single_edit` 单文件修改 | 修改或新建一个文件，校验落盘内容 | 写盘后崩溃、工具超时 |
| `multi_file` 多文件重构 | 一次修改跨多个文件，作为一个变更集原子落盘 | 写盘后崩溃、写入前被外部改动 |
| `mcp_tools` MCP 工具接入 | 通过 MCP 服务器读写外部状态 | 调用前崩溃、写入后崩溃 |
| `subtask` 受控子任务 | 父任务把只读调研交给子任务，用量结算回父任务 | 子任务内崩溃 |
| `memory_reuse` 经验复用 | 相关任务依次执行，后续任务可召回前面的经验 | 无（最后一个用例的预算只够走捷径） |

每个用例包含目标、初始文件、校验规则、离线脚本和可选的故障，例如：

```json
{
  "id": "edit-crash-after-write",
  "goal": "把 README.md 里的 TODO 换成测试命令说明",
  "files": {"README.md": "# Demo\n\nTODO\n"},
  "checks": [{"type": "file_equals", "path": "README.md",
              "content": "# Demo\n\n运行 `make test` 执行测试。\n"}],
  "script": {"turns": ["..."]},
  "fault": {"type": "crash_during_write", "kind": "files"}
}
```

## 故障

| 故障 | 模拟的情况 | 运行时要做对的事 |
| --- | --- | --- |
| `crash_before_tool` | 模型已要求调用工具、工具还没执行时进程被杀 | 续跑时执行这次调用，且只执行一次 |
| `crash_during_write` | 写盘完成、账本标记完成之前进程被杀 | 对账发现已写入，记为完成，不重写也不丢写 |
| `slow_tool` | 工具调用超过超时时间 | 按 `recovery.tool_retries` 重试 |
| `external_edit` | 写入前另一个进程改了同一个文件 | 识别冲突、不覆盖，重新规划后基于新内容修改 |
| `bad_call` | 模型给出不存在的工具或非法参数 | 把错误返回给模型，让它改正 |

崩溃类故障用继承 `BaseException` 的 `SimulatedCrash` 模拟进程被杀：恢复关闭时任务直接算失败；
恢复开启时用全新的运行时（不再注入故障）从检查点续跑，相当于进程重启。

## 策略

四种策略只是配置覆盖（`eval/runner.py` 的 `STRATEGIES`），模型和预算对所有策略相同：

| 策略 | 恢复 | 重新规划 | 记忆 |
| --- | --- | --- | --- |
| baseline（基础循环） | 关 | 0 | none |
| memory（记忆） | 关 | 0 | episodic |
| recovery（恢复） | 开 | 2 | none |
| full（记忆+恢复） | 开 | 2 | episodic |

同一任务族的用例按顺序在同一个状态库里运行，记忆策略能用上前面用例留下的经验；每个用例开始前重置工作区。

## 指标

- **成功率** = 通过全部校验的用例数 / 用例数
- **故障恢复率** = 注入故障的用例中最终成功的比例
- **每成功任务成本 / tokens** = 所有用例（含失败用例）的花费之和 / 成功用例数

成本按 `agent.toml` 里配置的价格计算；没配置价格时成本记为未知，不当成 0。

## 结果

### 真实模型（2026-11-19）

每个模型固定一个、预算相同，每种策略 18 个用例（9 个注入故障）：

| 模型 | 策略 | 成功率 | 故障恢复率 | 每成功任务 tokens |
| --- | --- | ---: | ---: | ---: |
| DeepSeek（deepseek-chat） | 基础循环 | 61% | 33% | 14,748 |
| | 记忆 | 61% | 33% | 15,211 |
| | 恢复 | 94% | 100% | 13,135 |
| | 记忆+恢复 | 94% | 100% | 11,866 |
| Qwen3-Coder（OpenRouter `qwen/qwen3-coder`） | 基础循环 | 56% | 33% | 21,732 |
| | 记忆 | 50% | 22% | 24,775 |
| | 恢复 | 83% | 100% | 15,140 |
| | 记忆+恢复 | 83% | 89% | 17,471 |

结论：

- 恢复机制是成功率差异的主要来源：两种模型上成功率分别提升 33 和 27 个百分点，每成功任务的 token 也更少。
- 关键词检索式的 episodic 记忆效果不稳定：相关任务上能省 token，无关任务上也可能分散模型注意力（Qwen3-Coder 上反而下降）。

### 离线（脚本模型）

离线模式下模型行为由脚本决定，验证的是运行时机制，不代表模型能力；成本按名义价格计算，只用于策略之间的相对比较。
脚本的 `variants` 模拟“看到相关经验就少走几步”的模型，使记忆策略的效果可测。

| 策略 | 成功率 | 故障恢复率 | 每成功任务 tokens |
| --- | ---: | ---: | ---: |
| 基础循环 | 50% | 11% | 3,139 |
| 记忆 | 56% | 11% | 2,673 |
| 恢复 | 94% | 100% | 2,239 |
| 记忆+恢复 | 100% | 100% | 2,077 |

按任务族的成功率：

| 任务族 | 基础循环 | 记忆 | 恢复 | 记忆+恢复 |
| --- | ---: | ---: | ---: | ---: |
| 只读问答 `read_qa` | 67% | 67% | 100% | 100% |
| 单文件修改 `single_edit` | 33% | 33% | 100% | 100% |
| 多文件重构 `multi_file` | 33% | 33% | 100% | 100% |
| MCP 工具接入 `mcp_tools` | 33% | 33% | 100% | 100% |
| 受控子任务 `subtask` | 67% | 67% | 100% | 100% |
| 经验复用 `memory_reuse` | 67% | 100% | 67% | 100% |

## 添加用例

1. 在 `evals/families/` 里新建或修改一个 JSON 文件，写好 `title`、`description` 和 `cases`（`family` 默认取文件名；可选的 `settings` 覆盖该任务族的配置）。
2. 每个用例写好 `goal`、`files`、`checks`；要参与离线评测还需要 `script`（格式见 `model/scripted.py` 的文档字符串）。
3. 运行 `mla eval --offline --only <任务族>` 确认结果符合预期，再提交。
